= Review locally with /code-review
:toc: left

[quote]
https://code.claude.com/docs/en/code-review-local#choose-what-to-review

* Run `/code-review` in a Claude Code session to find bugs in your branch's changes.
* You can point the review at a pull request or a path.
* Claude can apply the fixes.

'''

* `/code-review` is a command you type at the Claude Code prompt.
* You run it in the session where you are working.
* Claude reviews the changes on your branch and looks for correctness bugs.
* Claude reports what it found in your conversation.
* Depending on your model and effort level, the review also covers reuse,
  simplification, and efficiency cleanups.

'''

* The command works on any plan.
* The review runs in your own session.
* It counts toward your plan's usage or API billing the same way the rest of
  the session does.

'''

* `/review` is an alias of `/code-review`.
* Before v2.1.223, `/review` was a separate command.
* That command ran a single-pass, read-only review of a GitHub pull request.

'''

1 Run /code-review::
* Run the command.
+
....
/code-review
....
* With no target, the review covers the changes on your current branch.
* To point the review at a pull request, another branch, a path, or a range of
  commits, see Choose what to review.
+
'''
* You can also add flags.
`--fix`:::
** Also asks Claude to apply the findings to your working tree after the
   review.
** Its edits go through your permission mode.
`--comment`:::
** Posts the findings on a GitHub pull request as inline comments.
** On a GitLab merge request, posts the findings as a single note.

2 Keep working::
* In a terminal session, the review runs as a background subagent with its own
  context window.
* The subagent does not fill your conversation.
* The findings arrive in your conversation when the review completes.

3 Act on the findings::
* Ask Claude to fix what the review found.
* With `--fix` or `--comment`, Claude applies or posts the findings as part of
  the review, and you may be asked to approve its edits.

== Choose what to review

* To review something other than your current branch, type a target after the
  effort level and any flags.
* Claude receives that text as the review target.
* A target can be a pull request number, a branch name, a file path, or a Git
  revision range.
* Find what you want reviewed in the first column, and type what the second
  column shows.

[%header%autowidth,cols="d,m"]
|===
|To point the review at
|Type

|Your current branch and uncommitted changes
|/code-review

|Your last 15 commits
|/code-review HEAD~15..HEAD

|One branch against another
|/code-review main...my-feature

|A single commit, where `abc1234` is the commit's hash
|/code-review abc1234^..abc1234

|A pull request by number
|/code-review 1234

|A file or directory path
|/code-review src/auth
|===

* With no target, `/code-review` reviews your branch's commits ahead of its
  upstream branch, plus your uncommitted changes.
* If the branch has no upstream, Claude compares against `main`, or against
  the previous commit.

'''

* With `ultra`, Claude Code reads the target differently, as described in Text
  after the effort level and flags.

== What the review reads and edits

* Check these before you run a review, especially with `--fix`.

'''

Edits::
* Without `--fix`, the review's instructions ask Claude for a report only.
* With `--fix`, they also ask Claude to apply the findings to your working
  tree.
* Either way, any edit goes through your permission mode.
Rewinding::
* A background review applies its `--fix` edits outside your session's
  checkpoints.
* After one, `/rewind` restores only the files Claude had already edited in
  your conversation.
* The review's edits to other files stay, so use git to revert them.
* When the review runs in the foreground, it edits your working tree during
  your own turn, so `/rewind` restores its edits as usual.
Instructions::
* The review follows your `CLAUDE.md`, including in a non-interactive `-p`
  run.
* It does not read `REVIEW.md`.
* That file configures the managed Code Review service on GitHub pull
  requests.

== How findings are reported

* Claude reports the findings as text in the reply in both of these runs:
** In a terminal session, where `/code-review` runs the review as a forked subagent.
** In a `-p` run with text or JSON output.

'''

* In a host application that requests the findings list, such as the desktop
  app, Claude reports the findings through the `ReportFindings` tool instead.
* The report appears as a findings list.
* Each entry shows the file location, a one-sentence summary, and a category
  tag such as `correctness` when the finding carries one.
* A host request applies at every effort level.

'''
* When Claude fixes reported findings later in the session, it reports them
  again.
* Claude Code then marks each finding in the updated list as fixed, skipped,
  or no change needed.

== Tune effort and arguments

* Beyond `--fix` and `--comment`, the command takes these flags:

'''

`--post`::
* On an `ultra` cloud review of a `github.com` pull request, preselects
  posting the finished findings to the PR in the launch dialog.
* See Post findings to the pull request.
* Requires Claude Code v2.1.227 or later.

`--max-findings <n>`, `--max-findings all`, or `--max-findings default`::
* Reports up to `n` findings, or every finding with `all`, in place of the
  review's usual limit.
* Where the review reports through the findings tool, the limit is 32.
* Later reviews reuse the value you typed until you pass `--max-findings
  default`.
* A value passed in a non-interactive `-p` run is not remembered.
* Requires Claude Code v2.1.288 or later.

'''

* Pass an effort level to trade coverage for confidence.
* At `low`, the review reports the findings it is most confident in, so you
  see fewer false positives.
* From `medium` through `max`, the review broadens coverage.

'''

* When you don't type a level, the review reuses the last level from `low`
  through `max` you typed, even in an earlier session.
* Claude Code shows a notice such as `Reusing high effort, the level you typed
  last time`.

'''

* These rules decide which level a run uses:

'''

Typing a level::
* A level you type, like `/code-review high`, changes what later runs reuse.
Non-interactive runs::
* A level you pass in a non-interactive `-p` run does not update the
  remembered level.
`ultra`::
* The review neither uses nor updates the remembered level.
No level ever typed::
* The review uses the session's current effort.

'''

* Before v2.1.223, a `/code-review` without a level always used the session's
  current effort.

=== Text after the effort level and flags

* After the effort level and flags, Claude Code reads the rest of the line as the review target.
* The `ultra` argument changes that reading.

'''

With `ultra`::
* Claude Code reads a single word as a base branch or PR number.
* Longer text that does not name a branch or PR becomes a note attached to the review.
* `/code-review ultra check my auth changes h` reviews your current branch, and Claude relates the findings to your note.
Without `ultra`::
* Everything left is the review target, even when it starts with another command name.
* `/code-review /fix-issue 123` reviews with `/fix-issue 123` as target text.
* It does not load `/fix-issue` as a second stacked skill.

== Let Claude start the review

* Claude can start `/code-review` on its own, without you typing the command.

'''

When you ask in plain language::
* Ask Claude to review your changes, and it can run the skill.
From a scheduled task::
* A session-scoped scheduled task with `/code-review` as its prompt runs the
  review.

== Escalate to ultrareview

* `/code-review ultra --fix` runs the deeper ultrareview in the cloud.
* When the findings arrive back in your session, Claude applies them to your
  working tree.

'''

* Ultrareview uses its own scope.

'''

What it compares::
* Your current branch against the repository's default branch.
* Plus uncommitted and staged changes in the working tree.
Sensitive files::
* For uncommitted changes to files named like credentials or keys, such as
  `.env` and `*.tfvars` files, Claude Code follows the rules for uploading a
  local repository to a cloud session.
A different base::
* Pass a branch name to compare against a different base, such as
  `/code-review ultra develop`.

'''

* When the target is a `github.com` pull request, you can have Claude post the
  finished findings to the PR as a comment from your GitHub account.
* Requires Claude Code v2.1.227 or later.

NOTE: Ultrareview requires authentication with a claude.ai account.

* To run a cloud review from a script or CI job, use the `claude ultrareview`
  subcommand.
* That subcommand waits for the findings and prints them to stdout.
