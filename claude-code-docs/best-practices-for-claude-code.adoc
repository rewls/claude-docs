= Best practices for Claude Code
:toc: left
:source-highlighter: rouge
:revdate: 2026-11-07

[quote]
https://code.claude.com/docs/en/best-practices

[.lead]
Get more out of Claude Code: tell Claude what it can't see, give it a
check to run, and enforce the rules that can't have exceptions.

* Claude Code is built in a way that, in most cases, your first plain
  prompt in a fresh session already does the right thing, without any
  setup on your part.
* For example:

'''

* To let commands run safely without you approving each one, new
  terminal and VS Code sessions start in auto mode, where a classifier
  reviews anything risky before it runs.
* To keep your main conversation focused while independent work happens
  in parallel, Claude delegates to subagents and checks in only when it
  has to.
* To keep a long session going without you managing it, your
  conversation is compacted automatically before the context window
  fills.

'''

* This page covers what to do when the defaults aren't enough.
* That usually happens when your project has knowledge, rules, or
  constraints that Claude can't see from the code alone:

'''

* A deploy process that lives in someone's head
* A file that must never be read
* A check that has to pass before anything counts as done
* A budget you need to stay under

'''

* No default can know those things about your project, so this is where
  a small amount of setup on your side pays off.

'''

* When a session doesn't go the way you expected, it's almost always one
  of these:

'''

* Claude built something different from what you had in mind, or it has
  to rediscover the same fact at the start of every session. +
  It's missing information it can't get from reading the repo. See Tell
  Claude what it can't see.
* Claude said it was done and it wasn't quite, usually because it had no
  way to check its own work. See Give Claude a check to run.
* Claude did something that must never happen in this repo, or skipped a
  step that must always happen. +
  A prompt alone can't guarantee either of those. See Enforce the rules
  that can't have exceptions.
* Claude got it right, but it took more time, tokens, or permission
  prompts than the task was worth. See Change a default.

'''

* Let Claude run without you applies the same four points to unattended
  runs.
* What you can stop doing lists the advice that current models have made
  unnecessary.

== Deterministic and non-deterministic instructions

Every instruction you give Claude Code is one of these:

'''

Non-deterministic::
* You write the instruction, and Claude (the model) reads it.
* This can be your prompt, `CLAUDE.md`, or a skill.
* The model then decides what to do with this information.
* It usually follows your commands, and current models are good at
  understanding your intent without much context.
* There's no _guarantee_ that it'll follow your instructions.
* It can still decide not to do things, or do other things.

Deterministic::
* You configure the instruction, and Claude Code (the harness) _has_ to
  execute this.
* This can be a hook, a deny rule, or a managed setting.
* Claude Code applies this every time, no matter what the model decided
  to do.

'''

* Most things in Claude Code come in both forms:

[%header%autowidth,cols=3]
|===
|
|Non-deterministic (Claude decides)
|Deterministic (Claude Code enforces)

|What to do
|Your prompt, CLAUDE.md, skills Claude picks up itself
|Hooks, and which skills only you can start

|What it can touch
|Auto mode's classifier
|Deny rules, the sandbox in strict mode, managed settings

|When it's done
|A request for evidence, /goal, /code-review
|Tests, typecheck, a Stop hook, CI

|How much it spends
|Effort level, Claude's own pace
|`--max-turns` or `--max-budget-usd` with `-p`, a spend limit you've set

|Who has the last word
|Claude's summary of what it did
|Branch protection, a person who approves the merge
|===

'''

* Most of the time, you want Claude to decide.
* Almost every guideline has exceptions, and current models are good at
  reading the code in front of them and judging whether a guideline fits
  the situation.
* With the actual code in front of it, Claude is usually better placed to
  make that call than a rule you wrote in advance.

'''

* The deterministic kind is for when you want to make sure certain things
  _always_ happen (or never happen), no matter what the model decides.
* This doesn't have to be anything dramatic.
* Auto mode already blocks the dramatic things, like a production deploy
  or a force push over someone's work.
* It's usually something specific to _your_ project, and it can be as
  niche as you want it to be:
** Never edit the generated client in `src/gen/`
** Always run the license-header script after creating a file

'''

* You could've written either of these as a line in `CLAUDE.md` or in your
  prompt, and Claude would follow it nearly every time.
* But no matter how strongly you word it, whether Claude follows that line
  on a given turn is still Claude's call.

[TIP]
====
* If you keep adding emphasis to a CLAUDE.md line and Claude still misses
  it, that's a sign the line belongs in a hook.
* The reverse holds too: if you have hooks for things that are only
  preferences, delete them and let Claude decide.
====

== Tell Claude what it can't see

TIP: Only write down what Claude can't find by reading the repo, or what it would otherwise spend time rediscovering every session.

'''

* Claude starts every task by reading your code, and current models are
  _very_ good at this.
* They'll find your file layout, your conventions, your test framework, and
  how existing components are built, usually faster than you could explain
  them.
* That means Claude already knows most of what you might be tempted to write
  down for it.

'''

* What it can't find is the information that was never in the repo:

'''

* A decision your team made in a meeting
* A deploy process that lives in one person's head
* The environment variable your integration tests need

'''

* There's also information that _is_ in the repo but takes a few minutes of
  digging to find, and Claude has to redo that digging at the start of every
  session.

'''

* A good test before you write anything down for Claude:

'''

* Could it find this by reading the code?
* Would it actually go and look?

'''

* If both are yes, leave it out.

=== Write a specific prompt

* A specific prompt helps for the same reason, because it gives Claude
  information it doesn't already have.
* If you name the file, describe the symptom, and say what "fixed" looks
  like up front, you usually save yourself a round of corrections later.

'''

* The same goes for a preference between two reasonable approaches: Claude
  can't read that from the code, so if you care which one it picks, say so
  up front.

[%header%autowidth,cols="2*e"]
|===
|Instead of
|Try

|"fix the login bug"
|"users report login fails after the session times out. look at token refresh in src/auth/, write a failing test that reproduces it, then fix it"

|"add a calendar widget"
|"follow the pattern in HotDogWidget.php and build a calendar widget that lets you pick a month and page between years. no new libraries"
|===

'''

* If you already have the thing Claude needs, hand it over instead of
  describing it:

'''

* A file: type `@` and the path to include the file contents in your message.
* An image: paste the screenshot of the design or the error into the prompt.
* Command output: pipe it in from your shell with
  `cat error.log | claude -p "what's going on here"`.

'''

* Phrases like think step by step or be thorough are ordinary prompt text
  rather than keywords.
* The main control for how hard Claude thinks is the effort level, which
  Change the model and effort covers.
* Wording like that can still nudge Claude within its effort setting, but it
  won't lift it past it.

'''

* One phrase that does still help is be ambitious.
* Claude tends to read a request conservatively and build the smallest thing
  that satisfies it, since it can't see how much you were hoping for.
* When you want the fuller version, with the edge cases handled and the
  natural follow-on included, say so:

....
build the settings page from the mockup. be ambitious: empty and error states, the save flow wired up, keyboard navigation, not just the layout
....

'''

* That's telling Claude about scope, which only you know, rather than how
  hard to think.

'''

* When you're exploring rather than fixing something specific, a vague prompt
  like `what would you improve in this file?` is completely fine.
* You'll correct a bit more as you go, and that's the trade-off.

=== Brainstorm with Claude first

* When you don't know exactly what you want yet, you don't have to work it
  all out before you prompt.
* Ask Claude to interview you instead:

....
I want to add rate limiting to the public API but haven't thought it through yet. Interview me until you could write the spec, then write it to SPEC.md.
....

'''

* Claude comes back with multiple-choice questions about the parts you
  haven't pinned down: per-user versus per-key limits, what happens to
  requests over the limit, what's out of scope.
* It keeps asking until the answers add up to a spec.

'''

* Once `SPEC.md` exists, start a fresh session to build from it, so the build
  begins with a clean context and a written definition of done.
* It's also the file you'll point the reviewer at later, in Give Claude a
  check to run.

=== Keep CLAUDE.md short

* Claude Code loads `CLAUDE.md` into every session, which means every line in
  it takes a little of Claude's attention on _every_ task, whether it's
  relevant or not.
* That's why the file works best when it only holds what Claude couldn't work
  out from the code itself:

'''

* How to confirm work in this repo: the exact test, typecheck, and lint
  commands, and how to run a single test file
* Places where the code is misleading: an old pattern that's everywhere but
  that new code must not copy, or a directory that looks unused but isn't
* Decisions that aren't in the repo: which error helper the team settled on,
  how deploys work, what needs a migration review
* Anything you've had to correct twice already

'''

* A `CLAUDE.md` that passes that test stays short:

.`CLAUDE.md`
[source,markdown]
----
# Commands
- Install: pnpm install
- Run one test file: pnpm vitest run path/to/file.test.ts
- Typecheck: pnpm tsc --noEmit

# Conventions
- Use the error helpers in src/lib/errors.ts, never throw raw strings
- src/legacy/ is still live but don't copy its patterns into new code

# Gotchas
- Integration tests need DATABASE_URL set, see .env.example
----

'''

* In a session, run `/context all` to confirm that Claude loaded the file.

'''

* Notice that the typecheck line is only the command.
* Claude needs to know the command so it can check its own work as it goes.
* If you also want Claude Code to _enforce_ a passing typecheck before Claude
  finishes, that's a job for a `Stop` hook.
* A line like `Always typecheck before you finish` in this file works most of
  the time, not every time.

'''

* You don't have to write the file from scratch:

'''

* `/init` generates a starting version from your codebase. +
  From there the work is mostly removing lines. The memory guide recommends
  staying under 200.
* `/doctor` suggests cuts for anything Claude can already work out from the
  code.
* `/doctor prompt-audit` flags instructions that were written for older
  models, point at files that no longer exist, or contradict each other.

'''

* Your personal preferences go in `CLAUDE.local.md` instead of `CLAUDE.md`,
  and you add that file to `.gitignore` so it stays out of the repo.

[NOTE]
====
* If Claude keeps ignoring a line that _is_ in CLAUDE.md, adding IMPORTANT
  probably won't fix it.
* Either the file has grown long enough that the line gets lost, or the line
  is a rule that can't have exceptions, in which case it belongs in a hook.
====

== Give Claude a check to run

* Claude stops when the work looks done.
* If it has nothing to run that tells it whether the work actually _is_ done,
  "looks done" is all it has to go on.
* In practice that makes you the test suite, and every mistake sits there
  until you happen to notice it.

'''

* If you give it something that comes back pass or fail, Claude can close
  that loop itself.
* It makes the change, runs the check, and if something broke it reads the
  output and fixes it before running the check again.

'''

[TIP]
====
* Give Claude something it can run that comes back pass or fail. +
  Once it has that, it can keep going on its own and you don't have to watch.
====

'''

* The check can be almost anything, as long as Claude can read the result:
** A test file
** A build's exit code
** A linter
** A script that diffs output against a fixture
** A browser screenshot next to the mockup

'''

* If your repo already has one of these, the single most useful line in your
  `CLAUDE.md` is the command that runs it.

'''

* How strict you make the check is up to you.
* The options go from Claude deciding for itself all the way to Claude Code
  enforcing it:

'''

* In the prompt: `run the auth tests after, and keep going until they pass`.
  Claude decides for itself when it's satisfied.
  This works for any task, today, with no setup.
* As a goal: `/goal all tests in tests/auth pass and lint is clean` sets a
  condition that a separate model checks against the conversation after every
  turn, and Claude keeps going until it's met.
  You rarely need this in the session yourself.
  It matters for long background runs, where Claude sometimes ends a turn with
  a progress summary while items are still open, and the goal sends it back.
* As a `Stop` hook: a Stop hook runs your script whenever Claude tries to end
  its turn, and sends Claude back to work if the script exits with code 2.
  This one is enforced by Claude Code (the harness), so the turn doesn't end
  until the typecheck passes or the block limit is reached.
  There's an example further down.
* By someone who didn't write the code: in the terminal, `/code-review` reviews
  the diff in a fresh subagent that never saw your conversation.
  It isn't swayed by the reasoning that produced the code.

'''

* Whichever option you use, ask Claude for _evidence_: the command it ran and
  its output, or the screenshot.
* "All tests pass" on its own tells you very little, and reading the output is
  faster than rerunning the check yourself.
* For a session you weren't watching, it's also the only evidence you have.

'''

[TIP]
====
* Once Claude says it's done, you can also run `/verify` in the session, which
  has Claude build and run the app and look at the result. +
  That catches the kind of problem that tests and typechecks miss.
====

=== Review against your spec

* If you'd rather have the review check the work against your plan than hunt
  for bugs in general, write the review prompt yourself:

....
use a subagent to review the rate limiter diff against SPEC.md, check every requirement is implemented and the listed edge cases have tests, report gaps that affect correctness and skip style
....

[WARNING]
====
* Don't drop the `skip style` part of that prompt.
* A reviewer that's asked to find problems will always find something.
* If you fix every finding, you end up with extra abstraction layers and tests
  for cases that can't happen.
====

=== Enforce the check with a Stop hook

* The `Stop` hook version of the typecheck rule is a few lines in
  `.claude/settings.json`.
* Exit code 2 is what blocks the stop.
* Whatever the command prints to stderr goes back to Claude as the reason it
  can't finish yet, which is why the compiler output is redirected there:

[source,json]
----
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "pnpm tsc --noEmit 1>&2 || exit 2" }
        ]
      }
    ]
  }
}
----

'''

* To see it work, ask Claude for a change that breaks a type.
* Instead of finishing, it gets the compiler errors back and keeps going until
  `tsc` passes.
* If the hook blocks eight stops in a row with no tool call between them,
  Claude Code overrides the next block and ends the turn.
* To raise the cap, set `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`.

== Change a default

TIP: The defaults are good enough to leave alone until a task costs more time, tokens, or interruptions than it should.
When that happens, run /usage in the session to see where it went.

'''

* A new session already makes a handful of decisions for you:

'''

* Interactive terminal and VS Code sessions start in auto mode.
* It runs Claude Opus 5.5 at medium effort on most plans and providers.
* It delegates work to subagents when it sees a reason to.
* It compacts the conversation as it grows.

'''

* Most of the time you never think about these.
* When a task does cost more than it should, one of these four is usually why.

=== Know what subagents cost

* Claude delegates to subagents on its own:

'''

* Broad codebase searches go to the built-in Explore agent.
* Side tasks get forked while fork mode is on (the default).
* The subagents it starts run in the background by default, so your main
  conversation keeps moving.

'''

* You rarely need to ask for any of this, but it helps to know what you're
  getting and what it costs.

'''

* Subagents pay off in these situations:

'''

* Running independent pieces of work at the same time, so the whole task
  finishes sooner
* Keeping long output, like a full test run or a wide search, out of your
  main conversation, where it would otherwise ride along for the rest of the
  session
* Getting a reviewer that hasn't seen how the code was written
* Giving a task fewer tools than the main session has, like a reviewer that
  can read but not edit

'''

* What they cost you is mostly tokens, since every subagent sends its own
  requests and they count against the same usage as your main conversation.
* Sometimes it's time as well: a fresh subagent first has to gather context
  your conversation already had, so it can end up _slower_ than doing the
  task where you are.

'''

* And by default it's the same model (or a smaller one) on the same task.
* You get parallelism or a fresh pair of eyes out of it, but not a smarter
  answer.

'''

* To spend less on them:

'''

* Set `model:` haiku in a subagent's definition if its work is simple, like
  collecting the files that import a module or checking links in the docs. +
  That kind of job doesn't need the bigger model, and Haiku costs a lot less
  per request.
* Ask for short summaries back, so twenty results don't fill your context
  anyway.
* Check `/usage` to see what share of your usage each subagent type takes, so
  you can tell which ones are earning their cost.
* Give a custom subagent in `.claude/agents/` only `tools: Read, Grep, Glob`. +
  Now it's a reviewer that can't edit anything, and that limit is enforced by
  Claude Code rather than requested in a prompt.

'''

* That reviewer is one short file, `.claude/agents/reviewer.md`:

.`.claude/agents/reviewer.md`
[source,markdown]
----
---
name: reviewer
description: Reviews changed files against the spec they were built from. Use after implementing a feature, before opening the PR.
tools: Read, Grep, Glob
---
You're reviewing code you didn't write. Compare the changed files against the spec you're given,
check that every requirement is implemented and the listed edge cases have tests,
and report only the gaps that affect correctness. Skip style.
----

'''

* Ask Claude to `have the reviewer compare the rate limiter against SPEC.md`
  and the gaps come back into your session, where Claude can fix them.
